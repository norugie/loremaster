# CLAUDE.md — Loremaster working rules

Claude Code loads this file automatically at the start of every session. It holds the rules for how we work on this project. How the bot is built is described in `ARCHITECTURE.md`, and how to use it in `README.md`.

## Project in one paragraph

Loremaster is a Discord bot that answers members' lore questions from **any** roleplay server's Obsidian lore vault, and names the notes it used for each answer. It uses retrieval-augmented generation (RAG): it indexes the vault's notes, finds the ones relevant to a question, and has a local model answer from them. It runs on Youmu's Windows PC with local models through Ollama, alongside another bot. Each vault is described by its own config file kept with the vault, so any server can point the bot at their vault and get the same features; the first vault is Youmu's server's, but nothing about that server goes in the code or the repo. It is also a portfolio project and Youmu's first Python project.

## The loop (one change at a time)

The planned build is finished. For each new change Youmu asks for:

1. **Investigate.** Read the relevant code and docs. Check current library docs (see "Verify, don't assume").
2. **Plan.** Write a short plan: files to touch, approach, how it will be verified.
3. **Wait for Youmu's approval** of the plan.
4. **Implement** the smallest change that does what was asked.
5. **Verify.** Run the tests or a manual check. Show the output.
6. **Summarize** what changed and why, in plain language.

Keep `README.md` and `ARCHITECTURE.md` in step with the code. If the code and the docs disagree, stop and ask which one is right. Then fix the other one.

## Teaching mode

Youmu is learning, so:

- **Explain the "why".** For decisions specific to this domain (RAG, embeddings and vector search, chunking, prompting a local LLM, Discord bot events and permissions, GPU memory), give a brief plain-language explanation. Assume full-stack web experience, not domain experience.
- **Explain Python as we go.** This is Youmu's first Python project; they know JavaScript and TypeScript. When a Python concept shows up for the first time (virtual environments, packaging, type hints, `async`/`await` and the event loop, dataclasses, context managers, imports and modules, exceptions), explain it briefly and compare it to the JS/TS equivalent where there is one.

## Verify, don't assume

- Check current docs for every library used, before using an API. Key ones so far: Ollama and its Python client (`ollama`), Qwen3, nomic-embed-text, `discord.py`, SQLite (`sqlite3`) and `numpy`, `ruamel.yaml`, `pydantic`, `watchfiles`, Docker (`python:3.15-slim`, Compose), `uv` (inside the Dockerfile only), `pytest`, `mypy`, `ruff`. Add to this list as libraries are chosen in `ARCHITECTURE.md`.
- Prefer the official docs and the library's own source/README over blog posts.
- When you rely on a version number or API shape, say where you checked it.

## Coding style

- Python with type hints everywhere, checked by a type checker in strict mode (chosen in `ARCHITECTURE.md`). No `Any` unless there's a comment explaining why.
- Small modules with one job each. Pure functions where possible, so they're easy to unit test.
- Config comes from environment variables (secrets such as the Discord token) and the vault's config file (everything vault-specific), validated once at startup. Fail fast with a clear message if something is missing.
- Errors: never crash on one bad input. A malformed note, a bad frontmatter block or a failed question is logged and skipped, and the bot keeps going.
- Logs are short and useful: what happened, which id, how long it took. Never log secrets.
- Tests sit next to what they test or in a `tests/` folder (decided in `ARCHITECTURE.md`).
- Follow the folder structure in `ARCHITECTURE.md`. Changing it is an architecture change and needs approval.

## Smallest useful step

- No speculative architecture: build what the current change needs, not what a future one might need.
- No new dependency without asking first: say why it's needed and what the smaller alternative was.
- Fix root causes, not symptoms. If a workaround is unavoidable, say so.

## Never

- Never commit secrets or `.env`. `.env` stays in `.gitignore`; keep a `.env.example` with empty values instead.
- Never print `.env` values. In particular, don't run `docker compose config` without `--no-interpolate` (it prints every interpolated secret); check key names or lengths instead of values.
- Never add paid APIs or paid services. Models run locally through Ollama.
- Never let the bot use more than about 3 GB of GPU memory, even while answering; the PC shares its 12 GB GPU with another bot. Check with `nvidia-smi` when models or settings change.
- Never put lore in the repo: no sample vault, no vault content, no server-specific names, config or test data. Tests use small synthetic notes made up for the test.
- Never write to a lore vault except through `/lore update`. Indexing, answering and everything else only read it. Tests that write use a temporary made-up vault, never a real one.
- Never hard-code anything about a specific server or vault. If it differs between vaults, it goes in the vault's config file.
- Never call a change done without verifying it, and showing how it was verified.
- Never make large refactors that weren't asked for.
- Never run git commands that change history or the remote: no `git add`, commit, push, merge, rebase, or opening/editing PRs. Youmu does all of that from their local clone. Claude only edits files in the working tree and says what changed.
- Never change anything outside the repo without asking first.
